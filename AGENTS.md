# libskybrush-rs

A Rust rewrite of the C library [libskybrush](../libskybrush) (parsing and
playback of Skybrush drone show files), with feature parity to **libskybrush
6.0.4** where possible. The crate is called `skybrush`.

## Why it exists

The drone show part of the flight controller firmware is being rewritten in
Rust as a loadable ArduPilot module (ArduPilot PR #34814, a draft at the time
of writing). Existing C code keeps using the C library; new Rust code uses this
crate. **There is no C ABI requirement.**

What the module runtime implies (from the PR; re-check if it changes):

- Each module has its own heap, so `alloc` is available, but **heap growth while
  the drone is armed is capped**. Allocate when a show is loaded; playback
  (time updates, position/color/yaw queries, event iteration) must not allocate.
- Each module runs in its own thread: `Rc` is enough, `Arc` is not needed.
- Targets: STM32H7 (Cortex-M7 with FPU, `thumbv7em-none-eabihf`) and x86-64
  SITL. Modules need Rust 1.98.1 or later.
- Modules are trusted, privileged code without fault isolation. A Rust panic
  does not crash the firmware, but it parks the module's thread until reboot,
  so the show stops in flight.

## Ground rules

- **Idiomatic Rust over C conventions.** API quirks of the C library may be
  fixed. Prefer plain ownership and borrowing; use `Rc` only where data is
  really shared (e.g. a trajectory used by several scenes). Errors are
  `Result`s with error enums, not error codes. The public API follows the
  [Rust API guidelines](https://rust-lang.github.io/api-guidelines/checklist.html);
  deliberate deviations are recorded in `doc/rust-api-deviations.md`, with
  the reasons. Add an entry whenever the API departs from them on purpose.
- **`#![no_std]` + `alloc`.** No `std`, also not in the library's dependencies.
  Math functions come from the `libm` crate (`core` has no `powf`, `sqrtf`...).
- **No panics on malformed input.** `unwrap`, `expect`, `panic!` and slice
  indexing are denied by clippy (see `Cargo.toml`); report errors instead. The
  parsers will be fuzzed with `cargo-fuzz`.
- **No `unsafe`** in the library (`#![forbid(unsafe_code)]` in `src/lib.rs`).
  Tests may allow it where they need it, e.g. for a counting allocator.
- **Floating point:** `f32`, as in C. Be bit-exact with C only where it comes
  naturally (C is compiled with `-ffp-contract=off`, and Rust never fuses
  `a + b * c` unless `mul_add` is called). Never write convoluted arithmetic
  just to match C bit by bit; the golden traces have tolerances for this.
- **Naming:** structs are named after their C counterparts without the `sb_`
  prefix and the `_t` suffix (`sb_trajectory_player_t` → `TrajectoryPlayer`).
  Methods follow the names of the C functions unless a Rust convention overrides
  them (e.g. `sb_event_list_size()` → `len()`, `..._is_empty()` → `is_empty()`).
  Porting code that uses the C library should stay mechanical, so method names
  change only by the fixed rules in `doc/conventions.md` (`make` → `new`,
  `get_X` → `X`...). A type whose C name would be misleading in Rust gets a
  better name, listed in the same document (e.g. `sb_binary_file_parser_t` →
  `BinaryFile`, since it is a validated view of a file, not a parser with
  state).
- **Borrowed data is immutable.** In C, a trajectory loaded from a show file in
  memory is a view into the show file, and cutting or clearing it writes
  through to the show file (intentional, to save RAM on the flight
  controller). In Rust, a borrowed trajectory cannot be modified. Share data
  wherever possible and copy only when there is no other way: prefer a
  narrower view (a sub-slice, a new end time) to a modified copy, and own only
  the data that really changes (or use `Cow`). See `doc/conventions.md`.
- The minimum supported Rust version is 1.98.1 (`rust-version` in
  `Cargo.toml`); `rust-toolchain.toml` pins the stable channel with clippy,
  rustfmt and the Cortex-M7 target.

## The oracle: what parity means

Parity is checked against language-neutral test data generated by the C library
at the pinned commit (see below). The C unit tests are *not* the reference; they test the C
API, which this crate does not replicate.

| Data | Location | What it checks |
|---|---|---|
| Conformance cases | `../skybrush-file-formats-doc/spec/skyb/conformance/cases.json` (schema and README next to it) | Reading show files: block parsing, error codes, edge cases of the file format |
| Format traces | `../skybrush-file-formats-doc/spec/skyb/traces/*.json`, with the `.skyb` files and `tolerances.json` next to them | What can be read from a show file, sampled at 10 Hz: trajectory, yaw, lights, events, RTH plan entries, show controller output |
| API traces | `../libskybrush/test/api_traces/*.json` (see the `README.md` there) | What the library computes: statistics, cuts, landings, RTH conversion, builder, time axes, screenplays, event lists, light programs, motion and color helpers |

- The specification of the file format is in
  `../skybrush-file-formats-doc/doc/modules/skyb/pages/`. Where the spec and the
  C library disagree, ask; do not silently pick one.
- Deliberate differences from the C library's behaviour (approved by the
  maintainer) are recorded in `doc/differences-from-c.md`, with the reason and
  examples. Add an entry whenever the crate departs from C on purpose.
- Every trace records the inputs of each computation next to its results, so a
  test can replay it without the C library. Trajectories and light programs in
  the API scenarios are given as the hex-encoded bodies of their blocks.
- Errors are recorded by name: `SUCCESS`, `ENOMEM`, `EINVAL`, `EOPEN`,
  `ECLOSE`, `EREAD`, `EWRITE`, `EREADWRITE`, `EPARSE`, `TIMEOUT`, `ELOCKED`,
  `FAILURE`, `EUNSUPPORTED`, `EUNIMPLEMENTED`, `EPERM`, `EFULL`, `EEMPTY`,
  `EAGAIN`, `ENOENT`, `ECORRUPTED`, `EOVERFLOW`. The Rust test harness maps the
  crate's error enums to these names; the crate itself does not need them.
- Non-finite floats are recorded as `null`. The `generator` key is
  informational and is not compared.
- **Tolerances** depend on the suffix of the key, or of the closest enclosing
  array's key. A number matches if it differs from the golden value by at most
  `abs + rel * |golden|`. Integers without a known suffix (colors, timestamps
  and durations in milliseconds, counts, indices, flags) must match exactly.

  | Suffix | abs | rel | Notes |
  |---|---|---|---|
  | `_mm` | 0.01 | 1e-5 | |
  | `_mm_s` | 0.01 | 1e-4 | |
  | `_mm_s2` | 0.1 | 1e-3 | |
  | `_deg` | 0.001 | 1e-5 | |
  | `_deg_s` | 0.001 | 1e-4 | |
  | `_sec` | 0.001 | 0 | |
  | `_units` | 1.01 | 0 | API traces only: built trajectories in scale units, may differ by one quantization step |
  | `_approx8` | 1 | 0 | API traces only: 8-bit colors computed with `powf`/`logf` |
  | (default) | 0.0001 | 1e-5 | floats without a known suffix |

  The reference implementation of the comparison is
  `../libskybrush/test/traces/compare_traces.py`.
- The oracle is vendored into `tests/oracle` by `scripts/vendor-oracle.sh`,
  pinned to the tag `6.0.4` of libskybrush (commit `a6d4c4b`) and commit
  `7106669` of the spec repository; `tests/oracle/SOURCES` records the source
  commits. Do not edit it by hand, and do not let the tests read the sibling
  repositories directly. `scripts/vendor-oracle.sh --check` verifies it.

## Behaviour that is easy to get wrong

These were settled during the preparation of 6.0.0; the traces pin them down.

- **Scenes are placed on the show clock by their origins**, independently of
  each other (like clips in a sequencer): a scene covers
  `[origin, origin + duration)`, and the first scene in the screenplay that
  contains a time instant is the active one. There may be gaps (the show
  controller reports the end of the show there) and overlaps.
- **Origins must not be negative.**
- **Varints hold at most 32 bits.** In light programs, larger values are
  clamped to `u32::MAX` and execution continues after the varint. In RTH plans,
  entries that cannot be decoded (oversized varints, entry times beyond 32
  bits, durations above 2^24 s, missing points) do not invalidate the block;
  the plan stays usable up to the last entry before the first such entry, and
  lookups that reach it fail. Elsewhere, an oversized varint makes the block
  invalid.
- **Light program durations** are in frames of 20 ms; with 32-bit frame counts a
  wait can reach about 8.6 × 10^10 ms, so use `u64` milliseconds (the C
  library's 32-bit `unsigned long` wraps on the flight controller).
- **Pyro off events:** `add_pyro_off_events` extends every ignition to at least
  the given duration (the minimum ignition time of the pyro device); an
  explicit off event of a later firing of the same channel may be replaced by
  that. Off events that would end after `u32::MAX` are clamped to it.
- **Builder operations are all-or-nothing:** a failed operation leaves the
  builder intact.
- **Cuts and durations are calculated in integer milliseconds**; segment start
  times in seconds are rounded floats.
- **Replacing the end of a trajectory with a landing** limits the landing
  segment to 60 s.

## Plan

1. Vendor the oracle (a script that copies it from the sibling repositories at
   the pinned versions and records the source commits).
2. Write the conventions document (module layout, error enums, ownership,
   allocation rules, float policy, naming) for review.
3. Write the test harness before any library code: runners for the conformance
   cases, the format traces and the API traces, with the tolerance rules above.
4. Port the library, leaves first: varints, CRC32 and colors → trajectory →
   lights → events, yaw control, RTH plan, GCS light control, metadata → time
   axis and screenplay → show controller. Pause for review at each layer, since
   that is also where the shape of the API is decided.

Differential tests against the C library (linked as a test-only dependency) can
complement the oracle later, e.g. for fuzzed inputs.
